## Decisions

### 1. Persist the account-to-BGG association

Introduce `D20.Games.Favorite` and the focused `D20.Games.Favorites` context. Store `game_favorites` with non-null `user_id` referencing the existing string `users.id` with delete cascade, PostgreSQL integer `bgg_id` without a favorites-specific numeric range validator or positive CHECK, and UTC `inserted_at`. The composite primary key is `(user_id, bgg_id)`. No independent ID, update timestamp, mutable total, title snapshot, or local `games` foreign key is needed. The account-leading key supports batched membership reads; no global BGG aggregation index is needed.

Expose focused context operations to add, remove, and retrieve all current-account `Favorite` entities through `Favorites.list/1`, with `nil` returning `[]` and no compatibility alias. The list query filters only by the account and returns full entities without `order_by` or an ID-only `select`; it promises no ordering. PageController explicitly maps the returned entities to their `bgg_id` inside each existing lazy favorites prop, preserving the numeric frontend membership contract without exposing entity fields. The private query does not depend on catalog resolution. Detail route and Session validation still run before any successful detail response. Add uses insert-if-absent with the matching conflict target; only this duplicate is a successful no-op. Remove deletes only the authenticated account's matching association, and absence is success. Foreign-key, check-constraint, and operational failures remain errors. Deleting an account cascades its favorites; logging out does not delete them. Re-adding after removal creates a new timestamp.

Favorites remain attached to the original BGG ID if a local row changes binding, disappears, or becomes unavailable. A later page for that BGG identity still shows the saved state; favorites never grant launch permission. This iteration has no separate saved-game listing or promised metadata snapshot for permanently unresolvable games. An existing favorite can still be removed by its BGG identity without successful provider resolution.

### 2. Carry authoritative identity separately from metadata

Extend the resolved detail result with `bgg_id`, sourced from the selected local binding or successful parsed provider result. Keep the existing TypeID, normalized display slug, exact-local precedence, raw-string delegation, visibility rules, and provider-error behavior intact. Do not infer identity from titles, URLs, or TypeIDs.

Each home entry and resolved detail receives a `favorite` descriptor, serialized by the existing Inertia convention:

```typescript
favorite: {
    bggId: number;
    action: string;
    slug: string;
}
```

The static descriptor contains identity, one action URL, and original source context. Home and detail separately receive `favorites: number[]`, containing all saved BGG IDs for the current account from one query. Every control derives saved state from membership in this server prop. Guests receive `favorites: []` without an account query. No other account's membership, user list, counts, or saved metadata is exposed. A membership query failure must not fabricate an authoritative empty list; preserve the existing server error boundary.

The server constructs `action` as `/favorites/<resolved-bgg-id>`, with no query string and the exact same URL for PUT and DELETE. `slug` retains the original requested detail spelling rather than the normalized response slug; Home uses the delivered context slug. The descriptor never includes `session`, including when detail successfully renders an existing Session. Form fields carry source context instead of mutation-URL path/query data. Remove `addAction`/`removeAction` and their backend snake-case fields, without keeping a route alias.

For example, `/games/00183006` can resolve BGG 183006 even when exact local slug `183006` belongs to another BGG game. Reconstructing the submitted source slug from the normalized page slug could resolve the wrong subject. Preserve `slug: "00183006"`, use `action: "/favorites/183006"`, and compare the resolved source identity with the URL BGG ID before insertion. The client no longer sends a redundant hidden `bgg_id`.

### 3. Submit standard Inertia forms with safe redirects

Keep `GameFavoriteController` and the existing `:inertia` browser pipeline; use one resource path with explicit, idempotent methods:

| Request                     | Form data                                                                                  | Success                                |
| --------------------------- | ------------------------------------------------------------------------------------------ | -------------------------------------- |
| `PUT /favorites/:bgg_id`    | Original `slug` and `response_to`; no Session field; expected identity comes from the path | `303` redirect to the safe return page |
| `DELETE /favorites/:bgg_id` | `response_to`; any submitted `slug`/`session` is ignored and identity comes from the path  | `303` redirect to the safe return page |

Reuse session loading, actor/account resolution, secure headers, and the application's Inertia CSRF configuration. Resolve authentication from `conn.assigns.current_user`; do not require sudo or an email on provider-only accounts. Ignore client-supplied account identity. Validate `response_to` using `Auth.safe_local_path` and use the existing safe fallback when absent or invalid. This response target selects navigation only and never authorizes a game or Session.

For both methods, the HTTP boundary converts the generated URL `bgg_id` with standard `String.to_integer/1`, and the context accepts an integer. Remove custom regex, type/range checks and the `:invalid_bgg_id` response. Handcrafted malformed IDs use native conversion/query failure behavior without a dedicated favorite-form contract. Schema/database invariants remain intact; body/query fields cannot replace the path identity. PUT resolves the submitted original `slug` using `Games.fetch_by_slug/1` without invoking `Games.resolve_session/2`, a visibility predicate, or a runtime Session lookup. The caller supplies a string slug under the existing `Games.fetch_by_slug/1` input contract; Favorites adds no slug type or emptiness validation. Returned source-resolution failures retain the existing favorite error and safe redirect without a write; unexpected input-contract exceptions propagate. A resolved hidden local game is eligible by its BGG identity. Any submitted `session` field is ignored, regardless of whether it is absent, valid, mismatched or malformed. Compare the resolved BGG ID with the path ID before insertion. Launchability is irrelevant. The write never creates a local catalog row, a Session, or an interest record.

DELETE ignores source slug and Session fields, including invalid or obsolete values, and needs neither local visibility nor BGG availability: its sole authority is the authenticated account and its own association. An absent association succeeds without revealing whether another account saved that game.

No `PUT /games/:slug/favorite` alias remains. This changes the route/projection/form contract together, without a migration, dependency change, raw-header workaround, or persistence change. Deploy matching backend/client versions together; earlier open pages with the removed action need a reload.

Expected failures use `assign_errors` and the same safe `303` return flow. Authentication failure supplies an `authentication` error, refreshes `auth`, and performs no write. Unresolved games and changed bindings supply a concise `favorite` error, preserving their distinct failure meanings without a favorites-specific client notification. The previous JSON envelopes and 401/404/409/422/503 mutation status contract are removed. Existing framework CSRF rejection and unexpected-error behavior remain unchanged. Do not replace the JSON transport with `useHttp` or another custom HTTP wrapper.

### 4. Keep server props authoritative and make reloads selective

Use a reusable Inertia `<Form>` around each native favorite submit button. Always use `favorite.action`; current `favorites` membership determines PUT versus DELETE. PUT submits hidden `slug` and current-page `response_to`; DELETE submits only `response_to`. Neither method submits a hidden `bgg_id`. Source context remains in the descriptor for a later PUT. Neither method submits a runtime Session field. The return page retains its Session query as navigation context only, while the mutation action remains query-free. Configure `only: ["favorites", "auth", "errors"]`, `preserveState`, and `preserveScroll`. Inertia owns the request, current-cookie CSRF handling, processing, errors, cancellation, and page response lifecycle. Refreshed props are the sole saved-state authority: no copied membership map, manual fetch, cookie reader, `AbortController`, page generation, props-reset effect, navigation-disposal subscription, or retry registry remains.

Use ordinary `assign_prop` lazy functions and let the Inertia adapter select and evaluate props. Home assigns lazy `favorites`, `playable_games`, and `games` loaders in its normal rendering pipeline. A favorites/auth/errors partial response omits the collection props; the adapter may still evaluate their loaders and repeat catalog/BGG reads. Full responses retain existing selection, metadata projection, ordering, and provider-error fallback. Do not inspect raw partial-request headers, maintain a favorites-only allowlist, or add separate home/detail response branches. Standard adapter behavior governs full responses, matching or mismatched components, and partial `only`/`except` filtering.

Detail retains ordinary `Games.fetch_by_slug/1` and validated Session resolution before rendering. This preserves current not-found responses, Session-error redirects, original-route favorite source context, visibility policy, and flat page props. Assign favorites lazily and keep the independently computable launch `schema` value in a lazy function. Unrequested schema is omitted from the response; whether the adapter evaluates its callback is outside application acceptance. Do not restructure props, perform duplicate lookups, add memoization, or introduce a new exception framework to make the whole detail aggregate lazy.

A detail partial GET therefore still resolves the game and validates the supplied Session. It can make provider/Session reads and can fail when provider-only detail becomes unavailable or the Session is no longer valid. DELETE itself remains independent of provider availability and can persist removal before the following detail GET fails; a subsequent valid page load shows the saved membership. For a successful partial response, Inertia retains unrequested game, launch, and Session props and merges refreshed membership/auth/errors. No game or Session state is mutated by favorite operations.

The locked Inertia Elixir rc5 evaluates excluded lazy functions through `collect_once_meta_if_skipped/4`. The user accepts this redundant work and supersedes the former requirement to keep no-loader assertions failing. Retain both controller tests with ordinary provider fixtures; remove their failure-on-BGG stubs and the Home test's renamed catalog table. Assert successful add/remove, safe 303 redirects, private confirmed membership, authentication/errors, and omitted collection props without asserting loader or schema invocation counts. Preserve provider-independent DELETE mutation coverage and ordinary detail/Session validation. Keep lazy callbacks, frontend selective-prop requests, runtime code, and dependencies unchanged; add no header workaround.

Use the existing Inertia Form children snippet's local `processing` state in each FavoriteButton. Remove the page-local feedback object, `FavoriteFeedback` type, `favorites_feedback.svelte`, all `feedback`/`feedbackId` props and bindings, and result-based `aria-describedby`. Do not replace them with shared pending state, a context, store or notification service. Only the submitting form becomes busy; other occurrences and games are not disabled through favorites-owned coordination. They keep reading the same confirmed favorites prop, and ordinary Inertia request/cancellation behavior governs further submissions. Pending preserves the server-confirmed star and blocks repeat activation of that button without moving focus. Expected favorite errors and request failures leave the latest server props authoritative and the same control available for another explicit attempt once processing ends, without a custom success/error notice. Remove success/result, finish/reset, HTTP-error and network-error notification callbacks; retain only guest prevention and the authentication-error dialog callback. Standard adapter behavior handles HTTP/network failures. Retrying submits the current explicit PUT/DELETE through the same form. If a response is lost before fresh props arrive, retrying is safe because the server sets membership rather than toggling it.

For guests, prevent submission and open the existing account dialog with the current safe local return path. Closing it saves nothing. After login, fresh props show the account's favorites and another explicit click is required. An expired session returns an Inertia authentication error and refreshed auth through the same redirect flow, opens the existing dialog, and never automatically replays the write. Navigation/account changes use Inertia's page/request lifecycle without a favorites-specific reset/disposal system. Independent pages are not synchronized live; database execution order resolves their writes.

The installed `@inertiajs/svelte` 3.6.0 supplies the required form lifecycle. The official [forms](https://inertiajs.com/docs/v3/the-basics/forms) and [partial reloads](https://inertiajs.com/docs/v3/data-props/partial-reloads) documentation supports using form submission with selective props. Response filtering remains required; skipped callback execution is not an application guarantee. No new dependency is needed.
