## Why

The persisted catalog correctly moved operator-managed game bindings into PostgreSQL, but replacing the stable game slug with an environment-local TypeID at public-route and iframe-host boundaries made deployment addresses change across databases and broke the existing slug-addressed module infrastructure. D20 needs both identities: a database-generated TypeID for internal entity and Session relationships, and an operator-assigned immutable slug for stable external game and deployment addressing.

Owning issue: [#223 - Operators Can Manage Game Catalog Records](https://github.com/ravecat/d20/issues/223)

## What Changes

- Replace the hardcoded `D20.Games.Registry` configuration with persisted `games` rows and migrate all nineteen current entries.
- Keep `games.id` as a string-backed `game` TypeID generated by the owning database and use it for database identity, Session ownership, Workspace descriptors, module HTTP requests, socket scope, and signed module claims.
- Add required persisted `games.slug` as the operator-assigned, globally unique, DNS-safe, immutable external identity of every game, including planned games.
- Backfill the exact former registry slugs for all nineteen migrated games so existing public game URLs, local module hosts, Cloudflare Pages projects, and deployed static-module aliases remain stable.
- Restore slug-based catalog/detail/session-creation URLs and generate iframe hosts as `<slug>.<shell-host>` without deriving slug from BoardGameGeek metadata, engine module names, or TypeIDs.
- Store an editable positive unique `bgg_id`, `stage` (`planned`, `in_development`, or `released`), `enabled` flag, and nullable integer-backed engine enum with permanent module mappings.
- Require a valid engine for in-development and released records while allowing planned records to omit one.
- Make `enabled` an independent gate for new Session creation only. Disabled games remain discoverable, expose no launch action, and reject direct creation through both existing HTTP boundaries without affecting live Sessions or channels.
- Extend the protected Backpex game resource so authorized administrators can create games with required slug and BGG binding, and can list, show, and edit the existing mutable operational fields. Persisted `id` and `slug` remain read-only after creation; deletion remains unavailable.
- Protect the administration area with existing D20 account authentication and one shared persisted `admin` role requirement across HTTP and LiveView, while keeping the Bodyguard `D20.Games.Policy/:manage_games` capability check inside the Backpex game resource.
- **BREAKING:** Persist catalog identity and operational bindings instead of loading them from application configuration; update persistence, runtime lookup, contracts, admin behavior, and tests coherently while preserving the established slug-facing URLs and module hosts.
- **BREAKING:** Replace the optional `status` catalog contract with required `stage`; engine changes affect only Sessions created after the edit.
- Coordinate Infra to retain the explicit canonical slug set and remove TypeID-to-Pages aliases. Query-driven Infra reconciliation from a D20 deployment registry is deferred to a linked follow-up.

## Capabilities

### New Capabilities

- `game-catalog-administration`: Defines persisted game integrity, required immutable slug assignment, administrator create/edit behavior, protected Backpex access, and trusted database-managed administrator assignment.

### Modified Capabilities

- `playable-game-registry`: Replace the configured registry with persisted game records that carry both internal TypeID identity and stable external slug identity.
- `game-catalog`: Populate the catalog from persisted rows while retaining slug-based links.
- `game-catalog-availability`: Replace optional status with implementation stage and preserve the migrated catalog and ordering.
- `runtime-game-metadata`: Resolve presentation metadata by persisted `bgg_id` without deriving or owning the persisted slug.
- `game-metadata-fallback`: Keep slug-based catalog and detail access independent of runtime metadata availability.
- `game-detail`: Resolve persisted details by required game slug.
- `game-detail-activation-layout`: Preserve slug-based detail and Session-creation URLs while using persisted launch policy.
- `game-session-launch-policy`: Combine implementation-stage policy with the independent enabled gate at both HTTP creation boundaries.
- `game-session-creation-attrs`: Submit creation attributes and redirect lobby navigation through slug-based routes while creating Sessions under the resolved TypeID.
- `game-server-runtime`: Carry immutable local game TypeID in live Session server state and APIs.
- `koala-server-runtime`: Carry local game TypeID through the custom Koala Session server contract.
- `session-actor-registry`: Return attached runtimes associated with local game TypeID.
- `multi-session-game-workspace`: Discover and authorize Sessions by TypeID while framing their iframe with the persisted slug.
- `session-workspace-lifecycle`: Keep Workspace and SessionChannel scope association TypeID-based while preserving attachment and Presence behavior.
- `workspace-web-boundary`: Resolve persisted games by TypeID and use their slugs when building module framing data.
- `finished-session-workspace-access`: Preserve finished-Session access with TypeID-based descriptors.
- `client-workspace-state`: Consume the TypeID-based authoritative Workspace descriptor without client-owned normalization.
- `embedded-module-sandbox-policy`: Preserve the shared sandbox policy while deriving module origins from persisted game slugs.
- `game-module-frame-overlay`: Preserve frame behavior and bootstrap data under slug-based game URLs and iframe hosts with TypeID-based connection authority.
- `next-station-london-gameplay`: Preserve the game activation binding in the migrated persisted record.

## Impact

- Persistence: additive required `games.slug` with unique and DNS-safe constraints; generated environment-local `game` TypeID primary keys remain; all nineteen former slugs and operational bindings are backfilled; no BGG presentation columns are added.
- Backend: `D20.Games` schema/context and lookups, Session creation controllers, Workspace game resolution, module framing, router, and Backpex create/update behavior.
- Frontend/contracts: catalog and detail props expose both `id` and `slug`; browser navigation uses slug; Workspace and module connection contracts continue carrying `game_id` TypeIDs; iframe origins use persisted slug.
- Runtime compatibility: existing in-memory Sessions keep their captured TypeID and engine. Since slug is immutable, later mutable game edits do not move their module origin.
- External deployment: existing client repositories and local Traefik routes already use canonical slugs. Infra must remove exact TypeID aliases and continue provisioning the explicit slug-based Pages projects and domains before cutover.
- Deferred integration: D20 does not expose a deployment-registry endpoint and Infra does not query application state in this change; that reconciliation model requires a separately tracked contract and failure-safe lifecycle.
- Rollback: preceding TypeID-route code can ignore the additive slug column, but application routing and host aliases must move together. Keep canonical slug resources in place and temporarily retain or restore exact TypeID aliases only when rolling application code back to the TypeID-host release.
